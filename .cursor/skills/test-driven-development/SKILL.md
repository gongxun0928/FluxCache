# Test-Driven Development (TDD)

## 何时使用

用于：新功能、Bug 修复、重构/行为变更。  
例外（需确认）：一次性原型、纯配置改动。

## 核心原则

先 RED 后实现：**无失败测试在先 → 无生产代码**。

## Red-Green-Refactor

1. **RED**：写一个最小失败测试，描述期望行为。
2. **验证 RED**：运行测试，确认失败原因符合预期（缺能力/行为不对，而非笔误）。
3. **GREEN**：写最少代码让该测试通过。
4. **验证 GREEN**：运行测试，确认通过且其它测试仍通过。
5. **REFACTOR**：在保持全绿前提下整理重复、命名、结构。

每个新行为或边界情况：重复上述循环。

## 测试要求

- 一个测试只验一种行为。  
- 优先真实路径，必要时才 mock。  
- 测试名需清晰表达预期。

## 禁止行为

- 先写实现再补测试。  
- 未验证 RED 就继续实现。  
- 只测 mock、不测真实行为。  
- 为过新增测试而大规模删除/重写既有代码。  
- 允许回删范围：仅本轮新增且未稳定代码；不得删除既有稳定代码。

## 失败测试防失控护栏

1. 禁止破坏性兜底（删模块/绕分支/放宽断言）。  
2. 先缩小失败用例，定位测试问题还是实现问题。  
3. 每轮只改当前失败行为相关的最小路径。  
4. 修改前后跑受影响测试，防回归。  
5. 同一失败 3 轮无进展：停止改码，输出阻塞点与候选方案，请求人工决策。

## Bug 修复规则

先写能稳定复现该 bug 的失败测试，再改代码修复。
