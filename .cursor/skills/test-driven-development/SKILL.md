# Test-Driven Development (TDD)

## 何时使用

在实现以下内容时使用：

- 新功能
- Bug 修复
- 重构或行为变更

例外（需用户确认）：一次性原型、纯配置改动。

## 核心原则

**先有失败测试，再写生产代码。** 若没看到测试失败，就无法确认测试在测对的东西。

```
无失败测试在先 → 无生产代码
```

## Red-Green-Refactor

1. **RED**：写一个最小失败测试，描述期望行为。
2. **验证 RED**：运行测试，确认失败原因符合预期（缺能力/行为不对，而非笔误）。
3. **GREEN**：写最少代码让该测试通过。
4. **验证 GREEN**：运行测试，确认通过且其它测试仍通过。
5. **REFACTOR**：在保持全绿前提下整理重复、命名、结构。

每个新行为或边界情况：重复上述循环。

## 测试要求

- 一个测试只验证**一种行为**；名称说清行为。
- 优先用真实代码路径，仅在必要时 mock。
- 测试名称即文档：读 test 名就知道「应该发生什么」。

## 禁止行为

- 先写实现再补测试。
- 测试一写就过却继续实现（未确认 RED）。
- 保留现有实现作为“参考”再写测试。
- 用模糊测试名、只测 mock、不测真实行为。

若已发生以上情况：删除实现，从失败测试重写。

## 常见借口（简版）

- 太简单不用测 → 简单也会坏。
- 后面补测 → 无法证明测试有效。
- 手测过了 → 难复现、难回归。
- 先写再测一样 → 这是验证，不是 TDD。

## Bug 修复规则

先写能稳定复现该 bug 的失败测试，再改代码修复。
